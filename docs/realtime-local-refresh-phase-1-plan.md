# 实时更新第一阶段落地方案

## 1. 背景与目标

当前任务、Bug、异常、需求、事项池、版本页、我的工作台和空间总览主要依赖页面主动加载或用户手动刷新。后续系统中，多人协作、状态流转、评论、附件、标签、负责人和版本范围调整都会造成页面数据滞后。

第一阶段目标不是实现 Notion 级块编辑协同，而是先把业务对象级实时更新落地到主要页面，并保证刷新过程无感、稳定、不闪烁。

一期目标：

- 页面数据自动更新，不依赖用户手动刷新。
- 实时刷新不清空旧内容，不显示整页 loading，不出现骨架屏闪烁。
- 保留当前筛选条件、Tab、滚动位置、选中项、打开的详情抽屉和输入焦点。
- 可局部合并的数据优先局部更新，无法可靠合并时使用后台静默刷新兜底。
- 覆盖任务、Bug、异常、需求、事项池、版本页、我的工作台和空间总览。

非一期目标：

- 不做富文本多人协同编辑。
- 不做复杂 CRDT/OT 合并。
- 不把完整业务对象通过实时通道广播给前端。
- 不为每个字段都实现精确增量补丁。
- 不引入会明显改变部署复杂度的新基础设施，除非多实例部署已经明确需要。

## 2. 核心原则

### 2.1 实时事件只做失效通知

实时通道用于告诉前端“哪些数据可能变化了”，不直接替代现有查询接口。事件 payload 保持轻量，避免泄露超出当前用户权限范围的业务内容。

事件建议包含：

```ts
type RealtimeEvent = {
  id: string;
  sequence: number;
  occurredAt: string;
  actorId: string;
  organizationId: string;
  spaceId?: string;
  target?: {
    type:
      | "work_item"
      | "bug"
      | "exception"
      | "requirement"
      | "intake_item"
      | "version"
      | "comment"
      | "attachment"
      | "tag";
    id: string;
  };
  operation:
    | "created"
    | "updated"
    | "deleted"
    | "status_changed"
    | "assigned"
    | "tag_changed"
    | "commented"
    | "attachment_changed";
  invalidates: string[];
  hints?: {
    versionId?: string;
    requirementId?: string;
    assigneeId?: string;
    reporterId?: string;
    statusCategory?: string;
    workItemType?: string;
  };
};
```

### 2.2 前端刷新分模式

所有被实时事件触发的刷新都必须和首次加载区分。

```ts
type RefreshMode = "initial" | "manual" | "realtime";
```

- `initial`：首次进入页面，可以显示骨架屏或空状态。
- `manual`：用户手动刷新，可以显示按钮级 loading，但不清空旧内容。
- `realtime`：实时事件触发，只允许后台静默刷新，不允许整页 loading。

### 2.3 局部合并优先，静默刷新兜底

前端收到事件后按影响范围处理：

- 当前列表中存在目标对象：优先合并行/卡片的可见字段。
- 当前对象可能因为筛选条件进入或离开列表：静默刷新当前列表。
- 统计、Tab 数量、看板列数量：静默刷新对应聚合数据。
- 当前打开详情抽屉：静默刷新详情，但保留抽屉状态和用户输入。
- 当前用户正在编辑表单：不覆盖脏字段，必要时只更新只读区域或延迟到关闭弹窗后同步。

## 3. 技术架构

### 3.1 后端实时通道

推荐使用 SSE：

```text
GET /api/v1/realtime/events
```

选择 SSE 的原因：

- 当前场景主要是服务端向浏览器推送更新事件，SSE 足够。
- 前端原生 `EventSource` 可用，不需要新增 WebSocket 客户端依赖。
- 和现有 cookie session 鉴权模型兼容。
- 支持自动重连和 `Last-Event-ID`。

一期后端模块建议：

```text
apps/api/src/modules/realtime/
  realtime.module.ts
  realtime.controller.ts
  realtime-publisher.service.ts
  realtime-event.repository.ts
  realtime-event.types.ts
```

接口行为：

- 校验当前 session 和组织/空间权限。
- 根据用户可访问范围过滤事件。
- 支持浏览器断线重连。
- 支持 `Last-Event-ID` 后的事件补偿。

### 3.2 事件存储与分发

如果一期只有单实例 API，可以先用进程内事件分发加短期内存缓存。

如果考虑生产多实例部署，推荐直接使用 PostgreSQL outbox + `LISTEN/NOTIFY`：

```prisma
model RealtimeEvent {
  id             String   @id @db.Char(26)
  sequence       BigInt   @default(autoincrement())
  organizationId String   @map("organization_id") @db.Char(26)
  spaceId        String?  @map("space_id") @db.Char(26)
  actorId        String   @map("actor_id") @db.Char(26)
  targetType     String?  @map("target_type") @db.VarChar(40)
  targetId       String?  @map("target_id") @db.Char(26)
  operation      String   @db.VarChar(40)
  invalidates    Json
  hints          Json?
  occurredAt     DateTime @default(now()) @map("occurred_at")

  @@index([organizationId, sequence])
  @@index([spaceId, sequence])
  @@index([targetType, targetId])
  @@map("realtime_events")
}
```

写操作成功后：

```text
业务事务成功
  -> 写入 realtime_events
  -> pg_notify("crm_realtime_events", eventId)
  -> SSE 连接收到通知
  -> 按权限向浏览器推送
```

不要复用 `TimelineEvent` 作为实时事件表。时间线是用户可见业务记录，实时事件是技术失效通知，两者生命周期和语义不同。

### 3.3 前端实时基础设施

建议新增：

```text
apps/web/src/lib/realtime/
  realtime-client.ts
  realtime-provider.tsx
  use-realtime-invalidation.ts
  realtime-types.ts
```

核心职责：

- 建立 `EventSource` 连接。
- 处理断线重连和 `Last-Event-ID`。
- 根据当前页面注册的 invalidation key 分发事件。
- 对同一数据 key 做 200ms 到 500ms 合并防抖，避免一批写操作触发多次刷新。
- 暴露 `refresh({ mode: "realtime" })` 约定。

## 4. 页面覆盖范围

### 4.1 我的工作台

订阅范围：

- 当前用户相关工作项。
- 当前用户待处理动作。
- 当前用户负责、报告、关注或参与过的对象。
- 当前用户可见空间的近期活动。

影响区域：

- 待处理列表。
- 分配给我的任务/Bug/异常。
- 即将到期、逾期、阻塞项。
- 最近活动。
- 顶部统计。

刷新策略：

- 卡片存在时局部合并。
- 卡片可能新增或移除时静默刷新对应分组。
- 统计和最近活动独立静默刷新。
- 不重置当前展开、折叠和滚动状态。

### 4.2 空间总览

订阅范围：

- 当前空间下任务、Bug、异常、需求、事项池、版本和活动事件。

影响区域：

- 空间统计。
- 当前版本摘要。
- 任务/Bug/异常/需求数量。
- 最近活动。
- 风险或阻塞摘要。

刷新策略：

- 各区块独立静默刷新。
- 不清空旧总览数据。
- 不因为实时刷新让页面回到顶部。

### 4.3 任务页

订阅范围：

- 当前空间/版本/筛选范围内的工作项事件。
- 评论、附件、标签、负责人、状态和关联需求变化。

刷新策略：

- 当前行存在时局部合并编号、标签、创建人、时间、负责人、状态和标题摘要。
- 当前筛选条件可能受影响时静默刷新列表。
- 详情抽屉打开时静默刷新详情。

### 4.4 Bug 页

订阅范围：

- Bug 创建、更新、状态流转、负责人变化、标签变化、评论和附件变化。

刷新策略：

- 当前列表行局部合并。
- 状态、负责人、严重程度、标签影响筛选结果时静默刷新当前列表。
- 不清空筛选栏和分页状态。

### 4.5 异常页

订阅范围：

- 异常创建、更新、关闭、状态变化、负责人变化、标签变化。

刷新策略：

- 当前异常卡片/行局部合并。
- 标签筛选、状态筛选、负责人筛选受影响时静默刷新列表。
- 筛选入口保持和其他页面一致，不和 Tab 混在一起。

### 4.6 需求页

订阅范围：

- 需求创建、更新、状态变化、关联任务/Bug 数量变化、标签变化。

刷新策略：

- 当前需求行局部合并编号、标签、创建人和时间。
- 关联数量和统计静默刷新。
- 详情打开时只刷新详情数据，不关闭详情。

### 4.7 事项池

订阅范围：

- 事项创建、更新、状态流转、转换为任务/需求、标签变化。

刷新策略：

- 当前事项局部合并。
- 事项被转换或状态变化导致离开当前筛选时，静默从列表移除。
- 关联目标对象创建后，静默刷新对应关联区域。

### 4.8 版本页

订阅范围：

- 当前版本关联任务/Bug/需求变化。
- 工作项状态变化、类型变化、版本归属变化。
- 版本自身信息变化。

刷新策略：

- 看板卡片状态变化时局部移动到新列。
- 列数量和顶部统计静默刷新。
- 筛选栏位置稳定，和下方内容保持分割。
- 不因为看板刷新导致横向滚动或列宽抖动。

## 5. 写操作事件来源

一期至少覆盖以下写操作：

- 创建、更新、删除或关闭任务。
- 创建、更新、删除或关闭 Bug。
- 创建、更新、删除或关闭异常。
- 创建、更新、删除或归档需求。
- 创建、更新、接收、拒绝、延期或转换事项池事项。
- 版本创建、编辑、发布状态变化。
- 工作项状态流转。
- 负责人、报告人、优先级、严重程度、截止时间变化。
- 标签新增、移除、重命名或对象标签关系变化。
- 评论创建、编辑、删除。
- 附件上传、删除。
- 工作流动作执行。

事件发布应该放在业务服务层，而不是 controller 层，确保所有入口产生一致事件。

## 6. 前端无感刷新细则

### 6.1 禁止行为

实时刷新时禁止：

- 设置整页 `loading = true`。
- 清空当前列表或看板数据。
- 重置筛选条件。
- 重置分页。
- 关闭详情抽屉。
- 重置滚动位置。
- 抢占输入焦点。
- 在用户正在输入时覆盖表单字段。

### 6.2 允许行为

实时刷新时允许：

- 静默更新列表行字段。
- 静默移动看板卡片。
- 静默更新计数和统计。
- 轻量更新“最近更新于”时间。
- 对当前不可见的数据只更新缓存或下次进入时刷新。

### 6.3 冲突处理

如果用户正在编辑对象，同时收到远端更新：

- 不直接覆盖表单。
- 保留用户输入。
- 更新只读摘要或后台缓存。
- 用户保存时由后端做版本校验或更新时间校验。
- 如果保存冲突，提示用户重新确认。

## 7. 分阶段实施

### 7.1 第一阶段 A：后端实时事件基础

- 新增实时事件类型和共享 contract。
- 新增 SSE 接口。
- 新增事件发布服务。
- 在核心写操作中发布事件。
- 支持断线重连和事件补偿。

### 7.2 第一阶段 B：前端实时基础设施

- 新增 `RealtimeProvider`。
- 新增 `useRealtimeInvalidation`。
- 建立静默刷新约定。
- 为列表、看板、统计提供合并防抖。

### 7.3 第一阶段 C：页面接入

优先顺序建议：

1. 我的工作台。
2. 空间总览。
3. 任务页。
4. Bug 页。
5. 异常页。
6. 需求页。
7. 事项池。
8. 版本页。

原因：

- 我的工作台和空间总览是跨对象聚合页，最容易暴露数据滞后问题。
- 任务、Bug、异常是高频协作对象。
- 需求、事项池和版本页需要在列表、详情、统计和看板之间保持一致。

### 7.4 第一阶段 D：局部更新优化

- 为列表行建立稳定 merge 方法。
- 为看板卡片建立稳定移动方法。
- 为统计区块建立独立静默刷新。
- 为详情抽屉建立静默刷新但不关闭的模式。
- 对高频事件做合并防抖。

## 8. 验收标准

功能验收：

- A 用户修改任务状态，B 用户任务页自动更新。
- A 用户修改 Bug 标签，B 用户 Bug 页筛选结果自动同步。
- A 用户关闭异常，B 用户异常页列表和统计自动同步。
- A 用户新增需求，B 用户需求页和空间总览自动同步。
- A 用户转换事项池事项，B 用户事项池和相关任务/需求页面自动同步。
- A 用户调整版本内任务状态，B 用户版本看板卡片自动移动或静默刷新。
- A 用户操作当前用户相关事项，B 用户我的工作台自动同步。
- A 用户在空间内产生变更，B 用户空间总览自动同步。

体验验收：

- 实时刷新期间页面不闪烁。
- 列表不先变空再出现。
- 骨架屏只在首次加载出现。
- 当前筛选条件不丢失。
- 当前详情抽屉不关闭。
- 页面滚动位置不跳动。
- 用户正在输入的表单内容不被覆盖。

技术验收：

- SSE 鉴权生效，用户只能收到有权限范围内的事件。
- 断线重连后能补偿缺失事件。
- 批量事件不会造成重复请求风暴。
- 前端测试覆盖实时刷新不显示 skeleton 的场景。
- 后端测试覆盖写操作发布事件和权限过滤。

## 9. 风险与取舍

### 9.1 事件过粗导致刷新较多

一期可以接受部分静默刷新多于理论最小值，但必须避免整页闪烁。后续再根据性能指标细化 invalidation key。

### 9.2 多实例部署事件丢失

如果 API 会多实例部署，应直接采用 PostgreSQL outbox + `LISTEN/NOTIFY`。如果只做进程内分发，多实例下同一用户连接到不同实例时可能收不到另一实例发布的事件。

### 9.3 表单编辑冲突

一期不做实时协同编辑，只做保存时冲突校验。前端不覆盖脏表单，避免用户输入丢失。

### 9.4 权限过滤复杂

实时事件不要携带敏感业务内容。必要时只推 invalidation key，前端通过已有 API 拉取，仍由后端查询接口做最终权限控制。

## 10. 推荐结论

第一阶段应以 SSE 实时事件为基础，以局部静默刷新作为核心体验策略，以页面级 merge 作为优化点。

最重要的落地标准不是“所有字段都增量同步”，而是用户看不到页面重载痕迹：数据变新，但页面状态稳定、筛选稳定、输入稳定、滚动稳定。我的工作台和空间总览必须纳入第一阶段，否则聚合页会继续成为实时一致性的短板。
